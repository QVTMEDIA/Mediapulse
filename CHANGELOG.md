### Fixed

- **`composite_report` uploads rejected every row of a real vendor file with no Rating/GRP column.** Found live against a real user's file (`STATION`/`DAY`/`PROGRAMME`/`SPOT`/`RATE` columns, 2184 rows, no Rating or GRP column at all — matching the sample spreadsheet shape shown earlier in the session): the upload came back "0 rows mapped, 2184 skipped." Root cause: `parse_composite_report()` reused `grp_calculator.build_composite_report()`, which implements `app.py`'s different "Composite Report" concept — one workbook that already carries a vendor's own pre-computed Rating/GRP per row — and rejects any row with neither. `services/api`'s `composite_report` upload kind is a raw, multi-brand spot list; ratings get matched afterward by the Matching Engine, exactly like a `brand_report` upload, so requiring Rating/GRP up front was always wrong for this pipeline. A test fixture had quietly been working around this with a fake Rating column since Phase 2 — a sign this was already latent, just never triggered by a real file until now. Fixed by switching `parse_composite_report()` to `build_brand_report()` instead — it already reads a per-row `Brand` column (with the same filename-fallback) whenever `brand` is mapped, so the two builders only ever differed in the Rating/GRP requirement, not in brand handling. `grp_calculator.build_composite_report()` itself is untouched — `app.py`'s actual Composite Report screen still needs and uses its stricter validation. Removed the now-dead `'rating'`/`'grp'` mapping keys from `COMPOSITE_OPTIONAL_MAPPING_FIELDS`. New regression test uploads a file shaped exactly like the real one (Brand/Channel/Programme/Day/Spots/Rate, no Rating/GRP) and confirms it maps cleanly with resolved cost; verified further with a live smoke test reproducing the real file's exact column set end to end through the HTTP API.
- `db/schema.sql`'s `ratings.match_key`/`media_activity.match_key` `generated always as (...) stored` columns failed to apply on Supabase: `ERROR: 42P17: generation expression is not immutable`, even though `normalize_match_text()`/`normalize_match_day()` are declared `immutable` — the first time this schema was actually run against a live Postgres instance rather than only reviewed (see the caveat this confirms in `services/api/README.md`'s Tests section). Switched both columns to plain `text` columns set by a `before insert or update` trigger (`ratings_set_match_key()`/`media_activity_set_match_key()`) instead — triggers aren't held to the same provable-immutability bar generated columns are, and produce the identical value on every write. `services/api` never inserted into `match_key` explicitly (it always relied on this being computed automatically), so no application code needed to change. See the note in `db/README.md`.
- A `lambda instance=instance: instance` used to fix Python's closure late-binding when overriding several FastAPI `Depends()` in a loop (`tests/test_matches.py`) turned out to be its own bug: FastAPI treats a bare parameter on an override callable as a query parameter of the endpoint, which silently broke object identity across requests (a project created in one call became invisible to the next). Fixed with a proper zero-arg closure factory; documented in `services/api/README.md` so it doesn't get reintroduced in a future test file.
- `db/schema.sql`'s `match_key` generated columns assumed `day` was pre-normalized to a 3-letter code before storage and just did `upper(trim(day))`. `grp_calculator`'s real report builders don't normalize `Day` before storing it (only when computing a Match Key) — so a `day` value like "Monday" would produce a different SQL-side match key than the Python-side one for identical data. Added `normalize_match_day()` (a SQL port of `grp_calculator.DAY_MAP`) and switched both generated columns to use it. This was caught by building the real upload pipeline against the schema, not by a test — worth being suspicious of similar unverified assumptions elsewhere in the schema.
- Root `Dockerfile` never copied `project_store.py` into the image, so every built container failed with `ImportError` on startup (`app.py` imports it). `docker-build` in CI only builds the image, never runs it, so this had gone uncaught.
- `db/schema.sql`'s `match_key` generated columns didn't collapse internal whitespace or separate `programme`/`time_band` with a space, so they could disagree with `grp_calculator.make_key` on the same input; added `normalize_match_text()` to keep the two in lockstep.
- `services/api`'s DB connections had no `connect_timeout`, so a caller that forgot to override a repository dependency (as one of the initial tests did) would hang indefinitely against an unreachable database instead of failing fast.
