# Mediapulse API Service

FastAPI backend for the Vite/React frontend, implementing the target surface in `../../API_CONTRACT.md` against the schema in `../../db/schema.sql`.

## Status

| Resource | Status |
| --- | --- |
| `/api/health` | Done — not behind auth (a load balancer/orchestrator health check shouldn't need a token) |
| `/api/auth/register` + `/login` + `/me`, `/api/users` (list) + `/{userId}/role` (patch) | Done — real multi-user auth (Phase 3). Password hashing is PBKDF2-HMAC-SHA256 (`app/security.py`, stdlib `hashlib` only, no bcrypt/argon2 dependency); tokens are JWTs (`PyJWT`) verified by `app/auth.py:get_current_user`. ## Run locally

### Against Postgres (default)

```bash
docker compose up postgres   # from the repo root — applies db/schema.sql on first boot
cd services/api
pip install -r requirements.txt
export DATABASE_URL=postgresql://mediapulse:mediapulse@localhost:5432/mediapulse
python -m uvicorn app.main:app --reload --port 8000
```

### Without Postgres (in-memory repository)

Useful for frontend development or quick exploration when you don't want to stand up a database:

```bash
cd services/api
pip install -r requirements.txt
export API_REPOSITORY=memory
python -m uvicorn app.main:app --reload --port 8000
```

Data doesn't survive a restart in this mode — it's not a substitute for Postgres, just a faster loop.

Either way, interactive docs are at `http://localhost:8000/docs`. Almost every route needs a bearer token now — register a user first (`POST /api/auth/register`) and use its `accessToken`, either via `/docs`'s "Authorize" button or an `Authorization: Bearer <token>` header on direct calls.

Set `JWT_SECRET` to a real random value for anything beyond local exploration — it defaults to a hardcoded local-dev value (same pattern as `DATABASE_URL`'s `DEFAULT_DATABASE_URL`), which would let anyone forge a valid token if left in place on a real deployment.

## Deploying to production

This has actually been done once, on free tiers throughout: Postgres on Supabase, this service on Render, `packages/web` on Vercel. The repo root's `render.yaml` is a Render Blueprint that deploys `services/api`'s existing `Dockerfile` unmodified — no code changes needed to go from local `docker-compose` to a real deployment. Three environment variables have to be set in Render's dashboard (never committed — `render.yaml` marks them `sync: false`):

- `DATABASE_URL` — a Postgres connection string. On Supabase specifically, use the **Session pooler** string, not "Direct Connection" — the direct-connection host frequently fails to resolve (`getaddrinfo failed`) over IPv4-only networks, which most hosting platforms' outbound connections are.
- `JWT_SECRET` — a real random value (see above); generate one locally (`python -c "import secrets; print(secrets.token_hex(32))"`) rather than reusing anything that's ever appeared in a chat log or committed file.
- `ALLOWED_ORIGINS` — the deployed frontend's exact origin (e.g. `https://your-app.vercel.app`), **no trailing slash**. `app/main.py`'s CORS check is an exact string match against the browser's `Origin` header, which never has a trailing slash — leaving one in `ALLOWED_ORIGINS` means every request still gets rejected even though the value "looks right."

On the frontend side: `packages/web`'s `VITE_API_BASE_URL` has to be set on the hosting platform (Vercel, in the one real deployment so far) *before* the first production build, not after — Vite bakes `import.meta.env.VITE_*` values into the built JavaScript at build time, it doesn't read them at runtime the way a server-side env var works. Changing it later means triggering a new build, not just updating a dashboard setting.

**`db/schema.sql` has changed since the one real deployment above was set up.** Media spend/SOE added `media_activity.cost`, `grp_runs.total_spend`, `brand_shares.total_spend`/`.soe` — that `ALTER TABLE` pass has been run against the live Supabase instance and confirmed working (a real composite_report upload bug was found and fixed against that same production data afterward — see the Design notes below). Cable TV granularity added one more new column, `brand_shares.cable_tv_grps`, and the Spend Intelligence screen added three more, `brand_shares.tv_spend`/`cable_tv_spend`/`radio_spend` — **none of these four applied to the live instance as of this writing**; `media_activity.time_band` (daypart contribution) needed no migration since that column already existed in the schema unused. Flag pending schema changes explicitly rather than assuming they've shipped — this file is the place that tracks it.

## Tests

```bash
cd services/api
pip install -r requirements-dev.txt
python -m pytest -v
```

Tests never touch a real database — they override the `get_projects_repository` FastAPI dependency with a fresh `InMemoryProjectsRepository` per test (see `tests/test_projects.py`). `PostgresProjectsRepository` itself isn't exercised by the test suite; it's straightforward parameterized SQL against `db/schema.sql`, but it has been reviewed, not run against a live database (no Docker was available in the environment this was written in) — verify it against a real Postgres instance before relying on it for anything that matters. Adding a Postgres-backed integration test (e.g. via `testcontainers`) once CI has Docker access is the natural next step. This caveat was a real one, not boilerplate: the first time `db/schema.sql` was actually applied to a live instance (Supabase), it failed outright — see the `match_key` note in `db/README.md` and `CHANGELOG.md`. The Postgres repository *code* (the SQL in `app/repositories/*.py`) still hasn't been run against a live database end-to-end; only the schema file itself has now been verified to apply cleanly.

## Design notes

- **camelCase over the wire, snake_case in Python** — `app/schemas/common.py`'s `CamelModel` handles the conversion so route handlers and the repository layer stay in ordinary Python naming.
- **Repository pattern, not a direct ORM** — `app/repositories/projects.py` defines a `ProjectsRepository` protocol with a `PostgresProjectsRepository` (raw SQL, matches `db/schema.sql` columns 1:1) and an `InMemoryProjectsRepository` (tests, `API_REPOSITORY=memory`). Extend this same shape for the next resource rather than introducing an ORM mid-project.
- **One DB connection per request** (`app/db.py`) — the simplest thing that works for Phase 1 traffic. Swap in `psycopg_pool` when request volume makes that worth it.
- **`projects.owner_name` is free text**, matching current `app.py` behavior (no real user accounts yet). `projects.owner_id` exists in the schema but is unused until Phase 3 auth lands.
- **Duplicate semantics mirror `app.py`'s `duplicate_project()`**: new id, name suffixed " Copy", unarchived, fresh timestamps, everything else copied — including `status`, which is deliberately *not* reset.
- **`grp_calculator.py` (the Streamlit app's calculation engine, at the repo root) is imported directly** — `app/__init__.py` adds the repo root to `sys.path`, computed from `__file__` so it works identically locally and in Docker (see that file's comment, and the note at the top of `Dockerfile`). `app/matching.py` (match-key normalization) and `app/parsing.py` (brand-report upload parsing) both delegate to it rather than reimplementing it — this used to be a real duplication (`app/matching.py` had its own copy of `normalize_text`/`normalize_day`) until upload parsing needed the real module anyway, at which point duplicating was no longer the path of least resistance. If this service ever needs to run somewhere `grp_calculator.py` can't be shipped alongside it, that import needs revisiting — there's no fallback.
- **`db.get_connection()` sets `connect_timeout=5`** specifically so a test or caller that forgets to override a repository dependency fails in seconds instead of hanging on the OS TCP timeout against an unreachable database — this bit a test during development (see `CHANGELOG.md`).
- **Test fixture pitfall:** when overriding multiple `Depends()` in a loop, don't write `lambda instance=instance: instance` to dodge Python's late-binding closure bug. FastAPI inspects an override callable's *own* signature, and a bare (non-`Depends`) parameter becomes a query parameter of the endpoint it's injected into — so `instance` stops being "this closure's fixed value" and turns into something FastAPI tries to resolve per-request, silently breaking object identity across calls (a project created in one request becomes invisible to the next). This actually happened while writing `tests/test_matches.py`. Use a real zero-arg closure factory instead (`def _returning(instance): return lambda: instance`, called as `_returning(instance)` per loop iteration) — see that file.
- **Unmatched rows never get a `grp_calculations` row.** `db/schema.sql` makes `grp` `NOT NULL` there deliberately — "no rating available" and "confirmed zero GRP contribution" are different things, and blurring them into a 0 would make the audit trail lie. `grp_runs.unmatched_rows` is where that count lives instead.
- **A real bug, found by a failing test before it shipped: `detect_column`'s fuzzy substring matching can silently steal the wrong column.** Adding the `time_band` field for daypart contribution, an early synonym list included `'daypart'`/`'day part'`. `detect_column`'s fuzzy fallback (only reached when no synonym exactly matches any column) checks `canon(syn) in cc or cc in canon(syn)` — plain substring containment in either direction — so with a file that has no real daypart column at all, "day" (the exact text of the `day` field's own column) is trivially a substring of "daypart", and `time_band` silently grabbed the `Day` column instead of resolving to nothing. Fixed by dropping those two synonyms (`'time band'`/`'timeband'`/`'time belt'`/`'timebelt'`/`'time slot'`/`'slot'` cover the same real-world header names without the collision) and adding a regression test (`tests/test_grp_calculator.py:test_detect_column_time_band_does_not_steal_the_day_column`). Worth remembering next time a short/prefix-y synonym gets added to `SYNONYMS`: the fuzzy fallback has no concept of "this column is already spoken for" — it happily lets two different logical fields claim the same physical column.
- **That same daypart fix had a real side effect, caught live against a user's actual file, not by a test: `time_band` losing its old synonyms broke a legitimate case, not just the collision.** Before the fix above, `'time band'`/`'slot'`/etc. being `programme` synonyms meant a file with no distinct programme name at all — just a time-slot column (real radio audience-reach data commonly looks like this: `Channel`/`WD`/`Timeband`/`Rch %`, no `Programme`) — could still satisfy the *required* `programme` field via that synonym match. Removing those synonyms from `programme` (correctly, to fix the collision) left `programme` with nothing to fall back to for exactly this file shape, so every row failed `missing_match_field_mask`. `grp_calculator.resolve_effective_programme()` restores the fallback deliberately, not by re-adding the removed synonyms: it resolves `programme` and `time_band` as two independent columns (so the collision fix stays intact) and only substitutes `time_band`'s value in where a row's `programme` is blank. Applied in `build_ratings_lookup()`, `build_brand_report()`, and `build_composite_report()` — all three had the identical latent gap, not just ratings (`RATINGS_OPTIONAL_MAPPING_FIELDS` gained `'time_band'`, which it never had before). The lesson here is broader than this one bug: removing a synonym to fix a false-positive match can create a false-negative for a real file shape that synonym used to legitimately serve — check both directions, not just the one that motivated the change.
- **spot-volume-vs-GRP "weak inventory" flagging is a computed judgment call, not a stored fact — and the thresholds are opinions, not derived numbers.** `GET /runs/{runId}/spot-efficiency` (`app/routers/runs.py`) flags a brand/station combo when its GRP-per-spot is under half (`SPOT_EFFICIENCY_WEAK_RATIO = 0.5`) the category's own average for the run, and has at least 5 spots (`SPOT_EFFICIENCY_MIN_SPOTS`) so one unlucky placement doesn't trigger it. Both constants live at the top of `routers/runs.py`, deliberately conservative (they flag only clearly-below-average buys, not anything under the mean) since a false "weak" flag against a real advertiser's real campaign has real reputational cost, and deliberately not configurable per project yet — revisit if a real user needs a different bar. Computed fresh from `list_station_shares()` on every call rather than persisted, since "weak" only means anything relative to *this run's* category average, and would silently go stale the moment a later run changed that average.
- **The Spend Intelligence screen's "Overpriced" flag is spot-efficiency's mirror image, computed client-side rather than as its own endpoint.** `packages/web/src/sections/SpendIntelligenceSection.tsx` flags a brand when its cost-per-GRP (`totalSpend / totalGrps`) is over 1.5x the category average at 5+ spots — same conservative-threshold reasoning as spot-efficiency's `SPOT_EFFICIENCY_WEAK_RATIO`/`MIN_SPOTS`, just inverted (that one catches GRP too low for the spend; this one catches spend too high for the GRP). Deliberately kept as a v1 computed entirely from `BrandShare` fields the screen already fetches (`totalSpend`, `totalGrps`) rather than a new backend endpoint — brand-level cost efficiency doesn't need a join anything the frontend doesn't already have. A station/programme-level cost-efficiency view (mirroring `spot-efficiency`'s granularity) would need real backend work if a user asks for that level of detail later.
- **Share of Expenditure (SOE) deliberately counts unmatched rows; SOV deliberately doesn't.** `compute_run()`'s `spend_by_brand` accumulator runs unconditionally over every `media_activity` row, regardless of `is_calculable` — money was spent on a spot whether or not a rating was ever found for it, unlike GRP, which genuinely doesn't exist for an unmatched row. A project with zero matched rows can show `sov: 0` for every brand while still showing a fully populated, correct SOE breakdown — this is the one place in the calculation engine where two "share" metrics are computed from different row populations on purpose, not an inconsistency. `resolve_row_cost()` (`grp_calculator.py`) resolves each row's cost from a direct `Cost` column or `Spots x Rate`, `NaN`/`None` (not `0`) if neither was ever mapped — same convention as unmatched GRP. It uses `mapping.get('cost', ...)`, not `mapping['cost']`, because `app.py` builds a narrower `mapping` dict per screen that never includes `'cost'`/`'rate'` — a bracket lookup would `KeyError` there.
- **Formerly a known gap, now closed:** `POST /matches/{ratingMatchId}/correct` used to accept any `matchedRatingId` without checking it was a real rating attached to the project — a bad id just got stored and silently failed the `rating_by_id` lookup at `calculate` time instead of erroring where the caller could see it. Now validates against `ratings_repo.list_project_rating_rows()` and returns `422` immediately. This mattered enough to fix once `packages/web`'s Matches screen gained a manual rating picker (a real user could actually trigger the bad path, not just a hypothetical API caller).
- **CORS is open to the Vite dev/preview ports by default** (`ALLOWED_ORIGINS` env var in `app/main.py`, comma-separated) so `packages/web` can call this service directly from the browser. Tighten this for any real deployment.
- **`composite_report` uploads resolve brands per row, not per upload.** `parse_composite_report()` reads a `Brand` column via `grp_calculator.build_brand_report()` — not the similarly-named `build_composite_report()`, which implements `app.py`'s different concept of a workbook that already carries a vendor's own pre-computed Rating/GRP per row and rejects any row missing both. A real multi-brand vendor file (`STATION`/`SPOT`/`RATE`, no Rating/GRP at all — ratings are meant to be matched afterward by the Matching Engine) exposed this: every row came back rejected. `build_brand_report()` already reads a per-row `Brand` column the same way, with no such requirement, so it's the right function for this pipeline; `build_composite_report()` is untouched and still backs `app.py`'s actual Composite Report screen. The router then calls `get_or_create_brand(project_id, name)` — an atomic `INSERT ... ON CONFLICT (project_id, name) DO UPDATE ... RETURNING *` — once per distinct brand name found, and builds a `MediaActivityInsert(brand_id, row)` per row so each row lands under the right brand. `uploads.brand_id` is `null` for this kind since the upload itself doesn't belong to one brand.
- **Writing a dict to a `jsonb` column needs `psycopg.types.json.Jsonb(...)`**, not a bare dict — `PostgresMappingTemplatesRepository` wraps `field_mapping` this way on insert/update. Reading a `jsonb` column back auto-deserializes to a dict, no unwrapping needed.
- **Saved mapping templates degrade gracefully, never hard-fail.** `_resolve_mapping()` (`app/parsing.py`) only uses a template's saved column name for a field if that column still exists in the current file's header row; otherwise it falls back to `detect_column` auto-detection for that field alone, so a template that's gone stale (a source renamed one column) doesn't break the whole upload.
- **Auth is applied at the router level, not per-route.** Every router except `app/routers/auth.py` passes `dependencies=[Depends(get_current_user)]` to its `APIRouter(...)` call rather than adding `current_user: UserRecord = Depends(get_current_user)` to each route function — so a new route added to an existing router is authenticated by default, without anyone having to remember to add it. `app/routers/projects.py` is the one exception: `DELETE` needs a stricter `require_role('owner', 'admin')`, and `PATCH` needs to gate only the `archived` field, so those two routes take the dependency explicitly instead of (or in addition to) the router-level one.
- **Tests override `get_current_user` directly, not a real JWT.** `tests/_auth_helpers.py:make_test_user()` builds a fixed `UserRecord`; `app.dependency_overrides[get_current_user] = lambda: make_test_user()` (or `_returning(...)` in the dict-loop-pattern files) substitutes it everywhere the dependency is used — including inside `require_role(...)`'s closure, since that closure's own sub-dependency is `Depends(get_current_user)` and FastAPI resolves the override by that callable's identity. Passing `role=` to `make_test_user()` lets a specific test exercise the real 403 path (see `tests/test_auth.py`'s `test_member_cannot_delete_project`) without minting an actual token.
- **Deleting an upload/brand is refused, not silently allowed, once a run depends on it.** `media_activity.upload_id`/`.brand_id` are `ON DELETE CASCADE` in `db/schema.sql`, so Postgres *would* happily cascade-delete `rating_matches` and `grp_calculations` too if a caller could delete an upload/brand that had already been calculated — quietly rewriting a past run's audit trail out from under it, exactly what the audit rule at the top of `API_CONTRACT.md` exists to prevent. `app/routers/uploads.py`/`brands.py` guard against this explicitly: before deleting, they check `calculations_repo.has_calculations_for_media_activity()` and 409 if it's ever been true, rather than relying on "well, it usually won't happen." An upload/brand that's never been calculated (a duplicate, a mistake caught early) can always be removed. `matches_repo.delete_matches_for_media_activity()` is called explicitly before the delete too — redundant with the Postgres cascade, but load-bearing for the in-memory backend, which has no real foreign keys to cascade anything.
- **A real correctness bug, found and fixed this phase:** `pandas.to_datetime(..., dayfirst=True)` silently misreads an ISO-formatted date (`YYYY-MM-DD`) whenever the day and month are both ≤12 — e.g. `"2026-01-05"` parses as May 1st, not January 5th (pandas documents this as expected `dayfirst` behavior; it's still wrong for ISO input). This existed in both `grp_calculator.derive_day()` (used when a brand/composite report has a Date column but no separate Day column) and this service's own `app/parsing.py::_clean_date()`. A wrong derived day produces a wrong match key, which silently drops or misassigns rating matches — this is exactly the kind of bug the audit rule at the top of `API_CONTRACT.md` exists to catch. Fixed in both places by trying strict `format='%Y-%m-%d'` parsing first, falling back to `dayfirst=True` only when that fails; a regression test was added to `tests/test_grp_calculator.py`.

## Open decisions (see `../../db/README.md`)

Supabase vs. self-hosted Postgres, and whether to move off raw `psycopg` to SQLAlchemy or `supabase-py`, are not resolved by this service — it only assumes "a `DATABASE_URL` pointing at a Postgres speaking `db/schema.sql`," which holds either way.
